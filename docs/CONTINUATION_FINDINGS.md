- **المشكلة التي شوهدت:** تثبيت منتج (`locks: [{ productId, qty }]`) كان يُتجاهل بصمت — الخطة تختار منتجاً آخر لنفس الاحتياج، ولا يظهر أي تحذير. أثبت ذلك بسيناريو: قفل «فوكس 1121 أرز بسمتي 5 كيلو» بكمية 2 فاختارت الخطة «Kadhir Matta Rice» بدلاً منه.
- **السبب الجذري:** `lockMap` من نوع `Map`، لكن كل فحوص العضوية (13 موضعاً) استخدمت عامل `in` الذي يفحص خصائص الكائن لا مدخلات الخريطة — `"productId" in map` تُقيَّم دائماً بـ`false`. الخطأ موجود في الإصدار العام v2.0.0 ولم تلمسه جولات التطوير 2-3 لأن بيئتها بلا اعتمادات ولا اختبارات أقفال.
- **الملفات المتأثرة:** `src/lib/engine/generate.ts` (13 موضع `in lockMap` → `lockMap.has()`).
- **التعديل:** إضافة إلى إصلاح العضوية: حماية الأقفال من كل مسارات التعديل — سلّم العجز (خطوات 3-6)، سقف الترفيهات، طابور الترقيات الجشعة (لا تبديل ولا رفع كمية لمنتج مقفول)، والتحسين المحلي (كان محمياً سابقاً). وأضيف إنذار صريح «تعذّر تثبيت …» لكل قفل لا يمكن تنفيذه (معرف غير موجود / غير متوفر / محجوب / احتياجه غير مطلوب) بدل الإسقاط الصامت.
- **الاختبار:** 4 اختبارات جديدة في `tests/engine.test.cjs`: (1) القفل يظهر مرة واحدة بكميته المطلوبة ومعلَّماً locked ضمن fixedItems، (2) القفل يصمد تحت ميزانية متعذرة مع إعلان العجز رقمياً، (3) القفل غير القابل للتنفيذ يُعلن بسببه، (4) ظرف must تحت ميزانية ضيقة لا يتجاوز سقفه وspentFils يساوي مجموع أسطره والعجز معلن. النتيجة: **22/22 ناجحة، exit 0** (`bun run test`).
- **الأثر الجانبي المحتمل:** الخطط التي كانت تتجاهل أقفالاً ستراها الآن مصروفة ضمن fixedItems — إجماليات قد ترتفع قليلاً في سيناريوهات كان القفل فيها أغلى من اختيار المحرك، وهذا هو السلوك الصحيح. `getAllPlanItems()` لم يتغير.
- **المتبقي:** P1 — التحقق من أن واجهة قائمة التسوق والتقارير تعرض شارة القفل بوضوح، واختبار E2E لواجهة «ثبّت هذا المنتج» من شاشة المنتج.

### F-028: مصفوفة ثوابت الخطة تحققت فعلياً

- شغّلنا مصفوفة سيناريوهات: ميزانية سخية (توزيع طبيعي)، ميزانية ضيقة مع رضيع (عجز معلن 25,752 فلساً فوق هدف 57,000)، ميزانية مستحيلة 8,000 (عجز 71,174 معلن)، حتمية بايت-ببايت لنفس المدخلات، أظرف بأولوية must تحت ضيق، وقفل منتج بكمية. كلها طابقت الثوابت: مجموع الأسطر == إجمالي المحرك == إجمالي التشخيص، spendFils الظرف == مجموع أسطره ≤ سقفه، لا إنفاق فوق الهدف إلا مع عجز معلن صريح.
- E2E عبر متصفح فعلي: من الصفحة الرئيسية → تحليل النص الحر «أسرة من 4 أفراد وميزانيتنا 120 دينار» → معالج 7 خطوات → خطة 42 بنداً بـ113.959 د.ب من 120، مع تبويبات الأنماط الخمسة وسلّم التخفيضات الظاهر — صفر أخطاء Console/Page.
- **المتبقي:** P0 الأمني (مصفوفة API + rate limit + اختبارات مشاركة/خصوصية) واختبارات API تكاملية — انظر أولويات الجولة القادمة أدناه.

### F-029: بوابة الإدارة في وضع التطوير كانت تقبل أي مصدر (ترويسة Host لا تُقرأ)

- **المشكلة التي شوهدت:** طلب `GET /api/admin/stats` بترويسة `Host: external.example` يعيد 200 في وضع التطوير بلا مفتاح — أي أن «سماح loopback فقط» لم يكن يعمل، فأي عميل خارجي يصل للإدارة في وضع التطوير.
- **السبب الجذري:** الفحص استخدم `req.nextUrl.hostname`، وNext.js يحلها من عنوان الخادم نفسه دائماً (localhost) بغض النظر عن ترويسة Host التي يرسلها العميل — تحقق تجريبي عبر مسار probe أعاد `hostname:"localhost"` مع `host:"external.example"`.
- **الملفات المتأثرة:** `src/lib/server/admin-auth.ts`.
- **التعديل:** القرار الآن على ترويسة `host` الفعلية (مع فك أقواس IPv6 والمنفذ). وثّقنا بصراحة أن الترويسة قابلة للانتحال — هذا تسهيل للتطوير المحلي لا حد أمني؛ حد الأمن الحقيقي هو ضبط `ADMIN_API_KEY` في النشر (وإلا 503 في الإنتاج).
- **الاختبار:** `tests/api.test.cjs` — طلب بترويسة Host خارجية → 403، وطلب loopback مباشر → 200. ناجح (11/11).
- **الأثر الجانبي:** الوصول الإداري عبر الوكيل (Caddy) في وضع التطوير سيُرفض لأن Host سيكون النطاق العام — مقصود؛ استخدم مفتاحاً أو وصلاً مباشراً محلياً.
- **المتبقي:** P1 — اختبار وضع `ADMIN_API_KEY` المُهيأ (401/429 للتخمين) في CI بمتغيرات بيئة معزولة.
